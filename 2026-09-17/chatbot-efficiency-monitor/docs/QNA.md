# 발표 예상 질문과 답변

## Q1. 챗봇 사용량이 3배 늘었으면 비용만 늘어난 것 아닌가요?
사용량만 보면 판단할 수 없습니다. 도입 전 사람이 처리하던 건수, 챗봇 해결률, 상담원 전환율, 처리시간, 토큰 비용을 함께 비교해야 합니다. 3배 많은 문의를 처리하면서도 사람에게 넘어가는 건수가 줄고 순비용이 낮다면 처리 용량이 늘어난 것으로 볼 수 있습니다.

## Q2. 왜 SQLite를 사용했나요?
3명이 짧게 만드는 실습 프로젝트이고 별도 DB 서버 없이 파일 하나로 재현하기 쉽기 때문입니다. 실운영의 다중 사용자/다중 서버 환경이라면 PostgreSQL 같은 서버형 DB가 더 적합합니다.

## Q3. 가장 먼저 발생할 수 있는 운영 오류는 무엇인가요?
API timeout/429, 인증 실패, DB 연결/잠금, 로그 수집 누락, FAQ 데이터 오류가 대표적입니다. 먼저 HTTP 상태코드와 애플리케이션 로그를 확인하고, API latency/error 수치, DB 상태, 최근 배포 변경사항을 순서대로 확인합니다.

## Q4. 토큰 비용이 갑자기 늘면 무엇을 확인하나요?
세션 수 증가인지, 세션당 input/output token 증가인지 분리합니다. 이후 특정 카테고리, 반복 재질문, 긴 시스템 프롬프트, FAQ 라우팅 실패, 비업무 질문 증가를 확인합니다.

## Q5. CPU가 높으면 챗봇이 비효율적인 건가요?
아닙니다. CPU는 장애 분석 지표입니다. 챗봇 효율은 해결률, 상담원 전환, 처리시간, 비용과 함께 평가해야 합니다. CPU 상승이 응답 지연이나 오류와 동시에 발생할 때 원인 후보로 봅니다.

## Q6. 보안 질문은 왜 LLM에 보내지 않나요?
권한 부여나 보안 정책 변경은 잘못 처리했을 때 영향이 크기 때문입니다. 챗봇은 승인 절차와 담당자를 안내하고 실제 권한 변경은 기존 승인 시스템을 거치게 합니다.

## Q7. 직원 개인정보는 어떻게 보호하나요?
분석용 로그에는 최소한의 익명 식별자만 남기고 질문 원문 보관을 최소화합니다. 운영에서는 접근권한, 보관기간, 암호화, 마스킹, 감사로그 정책이 추가로 필요합니다.

## Q8. 챗봇이 잘못된 답변을 하면 어떻게 하나요?
어떤 FAQ/지식 버전을 사용했는지 추적 가능하게 하고, 낮은 신뢰도나 중요한 인사/보안/재무 질문은 담당자 확인으로 전환합니다. 잘못된 답변 비율도 별도 품질 KPI로 추가할 수 있습니다.

## Q9. API가 장애 나면요?
FAQ/클릭 메뉴는 계속 동작하게 하고 LLM이 필요한 질문은 '현재 AI 응답이 지연되고 있으니 담당자에게 문의'하도록 graceful fallback을 둡니다. 재시도는 무한 반복하지 않고 제한합니다.

## Q10. 비용 절감 계산이 완전히 정확한가요?
아닙니다. 이 프로젝트는 실습용 가정값을 사용합니다. 실제 도입 판단에서는 직무별 인건비, 인프라/보안/로그 비용, 실제 모델 단가, 유지보수 인력까지 포함해야 합니다. 그래서 대시보드의 단가를 설정값으로 분리했습니다.

## Q11. 어떤 회사에서 특히 효과적인가요?
직원 수가 어느 정도 있고, 전산/인사/총무 등 반복 문의가 많으며, 답변이 규정·절차·FAQ 형태로 표준화 가능한 회사에 적합합니다. 반대로 문의량이 매우 적거나 대부분 고도의 판단이 필요한 업무라면 효과가 작을 수 있습니다.

## Q12. 이상치 기능은 왜 필요한가요?
비업무 질문이나 특정 카테고리의 과도한 재질문, 긴 처리시간, 토큰 급증을 찾아 비용과 품질 문제를 빨리 발견하기 위해서입니다. 다만 직원 감시 목적이 아니라 서비스 개선용 집계 지표로 사용해야 합니다.
