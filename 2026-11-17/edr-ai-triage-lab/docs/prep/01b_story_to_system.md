# 사전 자료 1-2. 이야기에서 시스템으로: 우리가 만들 것과 고장 나는 곳

> 읽는 시간 10분. 01에서 본 '경비원 이야기'가 실제로 어떤 부품으로 만들어지는지 보고, 02(트러블슈팅)로 넘어갑니다.

## 1. 01의 이야기를 부품으로 바꾸면

01의 경비 비유에 나온 것들은 실습에서 각각 **하나의 프로그램(부품)**이 됩니다.

| 01의 비유 | 실습의 부품 | 하는 일 |
|---|---|---|
| CCTV 녹화 | **시뮬레이터** | 가상 회사 PC들의 활동 기록을 만들어 냄 |
| 녹화 보관함 | **OpenSearch** (`edr-events`) | 기록을 저장하고 검색할 수 있게 함 |
| 경보 규칙 | **탐지 프로그램** | 기록을 보다가 규칙에 걸리면 알림을 만듦 |
| 경보함 | **OpenSearch** (`edr-alerts`) | 처리를 기다리는 알림이 쌓이는 곳 |
| 경비원 | **워커** (LangGraph 에이전트) | 알림을 하나씩 꺼내 조사·판정·권고 |
| 경비 매뉴얼 | **OpenSearch** (`kb-playbooks`) | PDF 9종을 검색할 수 있게 넣어 둔 곳 |
| 경비원의 수첩 | **Postgres** | "어디까지 조사했는지"를 적어 둠. 승인을 기다리다가 이어서 할 때 필요 |
| 팀장의 승인 창구 | **API** | 분석가가 리포트를 보고 승인·거절하는 곳 |

## 2. 이 부품들은 어디서 돌아가나

모든 부품은 **가비아 서버 한 대** 위에서 돌아갑니다. 서버에는 **쿠버네티스(k3s)**를 설치하고, 각 부품은 컨테이너로 올라갑니다.

```
┌──────────────────── 가비아 서버 1대 (k3s) ────────────────────┐
│                                                                │
│  [시뮬레이터] ──기록──► [OpenSearch] ◄──조회── [워커(에이전트)] │
│                           ▲    │                    │    ▲     │
│  [탐지 프로그램] ──알림──┘    └────매뉴얼 검색─────┘    │     │
│                                                          │     │
│                              [Postgres] ◄──수첩──────────┘     │
│                                                                │
│  [API] ◄── 인터넷 ── 분석가(팀장)의 승인                         │
└────────────────────────────────────────────────────────────────┘
```

## 3. 알림 하나가 지나가는 길

01의 예시 알림(LSASS 덤프)이 부품들을 어떻게 지나가는지 따라가 봅니다.

1. **시뮬레이터**가 WS-007의 활동 기록을 만들어 **OpenSearch**에 넣는다.
2. **탐지 프로그램**이 "rundll32가 MiniDump 실행"을 발견하고 알림을 만든다.
3. **워커**가 알림을 꺼내 **OpenSearch**에서 기록을 조사하고(기록 담당의 도구), 매뉴얼을 찾는다(문서 담당의 검색).
4. 워커가 "격리 권고"를 쓰고, 팀장의 승인을 기다리며 **Postgres** 수첩에 진행 상황을 적어 둔다.
5. 팀장이 **API**에서 승인하면, 워커는 수첩을 보고 멈췄던 곳부터 이어서 리포트를 완성한다.

## 4. 그리고, 반드시 어딘가 고장 난다

부품이 많을수록 고장 날 곳도 많습니다. 같은 알림으로 예를 들어 볼게요.

| 이런 일이 생기면 | 우리 눈에 보이는 증상 |
|---|---|
| OpenSearch가 메모리 부족으로 꺼짐 | 에이전트가 기록을 못 찾아서, 악성인데 '의심'으로 판정함 |
| 워커가 멈춤 | 알림은 계속 쌓이는데 리포트가 하나도 안 나옴 |
| Postgres 비밀번호가 틀림 | 팀장이 승인했는데 리포트가 완성되지 않음 |
| 인터넷 연결 설정이 틀림 | 팀장이 승인 화면에 들어가지 못함 (에러 페이지) |

**증상은 맨 끝(리포트, 승인 화면)에서 보이지만, 원인은 대개 중간 부품에 있습니다.**
그래서 "어디서 멈췄는지"를 차근차근 찾아가는 방법이 필요합니다.

## 5. 이 방법은 01의 분석가가 일하던 방식과 같다

01에서 분석가는 알림을 받으면 **추측하지 않고 기록을 보며, 가설을 세우고, 확인한 근거로만 판단**했습니다. 고장 난 시스템을 고치는 엔지니어도 똑같이 일합니다.

| 01: 분석가가 알림을 조사할 때 | 02: 엔지니어가 고장을 조사할 때 |
|---|---|
| 알림이 울림 | "승인이 안 돼요" 같은 신고가 들어옴 |
| 급한 것부터 가름 | 급한 것부터 가름. 되돌릴 수 있으면 먼저 되돌림 |
| 추측하지 않고 **PC의 기록**을 봄 | 추측하지 않고 **부품의 로그·상태**를 봄 |
| "악성인가?" 가설 → 기록으로 확인 | "OpenSearch가 꺼졌나?" 가설 → 명령어로 확인 |
| 확인한 근거로만 판정 | 확인한 원인으로만 고침 |
| 트리아지 리포트 작성 | 런북(고장 대응 기록) 작성 |

이번 실습에서는 둘 다 합니다. **에이전트를 만들면서 분석가의 방식을 코드로 옮기고**, **그 에이전트를 서버에 올리면서 엔지니어의 방식을 직접 해 봅니다.**
