## 1. 👥 에이전트 완성

### 1-1. 가짜 도구를 진짜로 바꾸기
- `mocks.py` 대신 🔍 기록 담당의 조사 도구 3개와 📘 문서 담당의 `search_playbook`을 연결합니다.
- **한쪽 도구가 아직 덜 됐다면:** 그 도구만 가짜로 두고 다음 단계로 갑니다. 담당자는 틈틈이 마무리하고, 끝나면 바꿔 끼웁니다. 계약을 지켰다면 에이전트 코드는 고치지 않아도 됩니다.
- **계약 위반이 있으면 여기서 드러납니다.** 그럴 때는 누구 탓도 아니고, `docs/CONTRACT.md`를 고치고 변경 이력에 적습니다.

## 2. 👥 평가 기준점

**왜:** 3일차 고도화가 "좋아졌다"를 증명하려면 **지금의 점수**가 있어야 합니다. 서버에 올리기 전에, 그리고 교차 작업으로 무언가를 바꾸기 전에 **내 PC에서** 잽니다.

```bash
python -m soc.eval.rag_eval                 # 📘 RAG: 정답 문서가 상위 3개 안에 드는 비율 (21문항)
python -m soc.eval.agent_eval --n 12        # 👥 에이전트: 판정 정확도, 지어낸 근거 비율, 승인 요청 비율, 응답 속도, 알림당 비용
```

1. 결과를 `docs/DECISIONS.md`의 "평가: 기준점"에 붙여 넣습니다.
2. **틀린 사례 2개를 골라, 어느 단계에서 틀렸는지** 원인까지 적습니다. 02 문서 5장의 표(도구 / RAG / 판정)를 펴 놓고 쪼개 보세요.
   - 🔍 기록 담당: 도구가 근거 기록을 제대로 돌려줬나?
   - 📘 문서 담당: 정답 문서가 검색 상위에 있었나?

✅ **확인:** 기준점 표가 채워져 있고, 틀린 사례 2개의 원인 단계가 적혀 있다.

## 4. 👥 🔥 인프라 1~5단계

### 단계 진행
[`INFRA_STAGES.md`](INFRA_STAGES.md)의 1~5단계를 진행합니다. 단계마다 **만들기 → 깨 보기 → 진단 후 나눔 → 런북 기록** 순서입니다. 진단 후 나눔은 진단자가 가장 오래 걸린 지점을, 출제자가 '나라면 어디부터 봤을지'를 이야기하고, 둘이 '다음에 처음 칠 명령 하나'를 정하는 단계입니다 (`INFRA_STAGES.md` 깨 보기 규칙 5~6번).
깨 보기는 **단계마다 필수 문제를 먼저** 하고, 여유가 있을 때 목록의 다른 문제를 더 합니다.

| 단계 | 운전 | 만드는 것 | 필수 깨 보기 | 이 문제를 고른 이유 |
|---|---|---|---|---|
| 1 | 📘 | 서버, k3s, 첫 Deployment | 1-1 이미지 태그 오타 | 가장 자주 만나는 배포 장애 |
| 2 | 🔍 | OpenSearch (StatefulSet). **시작 전에 `docs/CAPACITY.md` 계산** | 2-1 커널 설정 되돌리기 | 02 문서 8장 '좋은 런북' 예시의 장애 |
| 3 | 📘 | Postgres, Secret, ConfigMap | 3-2 비밀번호만 변경 | 02 문서 9-1에서 명령 결과로 풀어 본 장애 |
| 4 | 🔍 | 워커, 생성기, 상태 확인(프로브) | 4-3 워커 정지, 4-5 처리 중 워커 삭제 | 01b 문서 4장의 "워커가 멈춤"과 3장 5번의 "수첩을 보고 멈췄던 곳부터 이어서" |
| 5 | 📘 | Ingress (외부 공개) | 5-2 Service selector 오타 | 01b 문서 4장의 "승인 화면에 들어가지 못함" |
